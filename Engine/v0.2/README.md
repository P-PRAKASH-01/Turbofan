# ENGINE-TWIN synthetic dataset v0.2.0

## Status and use

Version 0.2 is a deterministic, assumption-driven synthetic simulator and dataset for prototyping a piston-engine digital-twin data workflow. It is **not a validated real-engine digital twin** and does not model a specific manufacturer, aircraft, or DRDO engine. It is not for flight, maintenance, safety decisions, operating limits, or real-engine accuracy claims.

The simulator is a transparent, quasi-steady surrogate with simple first-order thermal response. It is intentionally not described as a validated Mean Value Engine Model (MVEM): no target-engine specification or calibration data was supplied. Constants marked as physical standards are used only in their standard mathematical role; all engine and fault-response parameters are project assumptions listed in `config/dataset_config.json` and `metadata/parameter_register.csv`.

No health-index or RUL target is produced. `rul_hours` remains null because there is no degradation-to-end-of-life model.

## Reproduce

Supported Python version: **Python 3.11**. The recorded environment used Python 3.11.0, NumPy 2.3.3, pandas 3.0.1, scikit-learn 1.7.2, and joblib 1.5.2. These direct dependency versions are pinned in this directory's `requirements.txt`; transitive dependencies are not locked, so a clean environment with another resolved dependency stack has not been verified.

From the repository root, enter this v0.2 directory and create an isolated environment:

```powershell
Set-Location '.\Engine\v0.2'
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Run the pipeline in this order: **generation → feature building → validation → tests → baseline training**.

```powershell
.\.venv\Scripts\python.exe -m src.generate_dataset
.\.venv\Scripts\python.exe -m src.build_features
.\.venv\Scripts\python.exe -m src.validate_dataset
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m src.train_baselines
```

The generator, feature builder, validator, and baseline trainer default to this v0.2 directory. Generation rewrites generated raw data, manifests, dataset card, and split files; feature building rewrites processed tables and feature metadata; validation and training rewrite their reports, and training also rewrites model artifacts. To preserve this checked-in dataset and its results, copy the complete `v0.2/` directory and execute the commands from that copy. The tests read the v0.2 data and do not form a generation step.

The generator's default seed is `314159`. It uses NumPy's `default_rng` (PCG64); scenario IDs are generated by a separate RNG stream seeded from the master seed and a fixed independent stream tag. Each scenario has its own seed in `metadata/scenario_manifest.csv`. The card records the config/generator hashes and the data/manifests/split hashes. Byte-identical regeneration was verified for the recorded environment and project source; this does not establish byte identity across unpinned transitive dependencies or other platforms. See `metadata/schema_and_artifact_inventory.md` for exact processed schemas, partition sizes, and current artifact checksums.

To use a different deterministic seed, copy the JSON config into a separate run directory, change `seed`, then pass both `--config` and `--output-dir`; do not overwrite this checked dataset if preserving its hashes.

## Scenario and split design

- 30 synthetic engine parameter sets: 18 training engines, 6 validation engines, 6 held-out test engines.
- Every engine has a scenario for each combination of 8 fault classes and 4 operating phases, giving 32 scenarios per engine.
- Each scenario contains 120 samples at 1 second intervals.
- Fault class is crossed with every phase. Nominal altitude, ambient-temperature offset, and throttle are sampled independently of class, severity, and phase. Severity is selected independently for each non-normal scenario.
- Scenario IDs are opaque 64-bit random hexadecimal tokens assigned independently of scenario labels. Engine IDs are similarly opaque.
- **Scenario-held-out protocol:** the 18 training-engine scenarios are stratified into train/validation/scenario-test partitions jointly by fault type and operating phase. Every fault/phase pairing is covered in each partition. Engine identities recur across these scenario partitions by design.
- **Engine-held-out protocol:** train, validation, and test use disjoint engine IDs. The six test engines appear in neither engine-training nor engine-validation.
- All nine engine-held-out and scenario-held-out split files are in `splits/`; the full scenario and engine manifests are in `metadata/`.

## Assumption-driven equations

All variables are in SI units unless the unit appears in the name. Let altitude be `h` (m), ambient offset be `ΔT` (K or equivalently °C difference), normalized throttle be `u = throttle_pct / 100`, displacement be `Vd` (m³), engine speed be `n` (rev/min), and `Rair = 287.05 J/(kg K)`.

### Ambient condition

For the sampled 0–5000 m range, use a constant-lapse troposphere approximation:

```text
Tstandard_K = 288.15 - 0.0065 * h
Tambient_K = Tambient_C + 273.15
Tambient_C = Tstandard_K - 273.15 + ΔT + temporal_variation
pambient = 101325 * (1 - 0.0065*h/288.15)^(9.80665/(Rair*0.0065))
rho = pambient / (Rair * Tambient_K)
```

Pressure depends on altitude, not the independent temperature offset; density uses the actual sampled ambient temperature. This is an approximate atmosphere input, not an environmental certification model.

### Intake, speed, fuel, power, torque

```text
pmanifold = pambient * (0.28 + 0.70*u)
nhealthy = nidle + (nrated - nidle)*u^0.5 * clip((rho/rhoSL)^0.05, 0.95, 1.02)
rhoSL = 101325 / (Rair*288.15)
mair = (pmanifold/(Rair*Tambient_K)) * Vd * (n/120) * volumetric_efficiency
mfuel = mair / 14.7
Pshaft_W = mfuel * 43,000,000 * thermal_efficiency
Pshaft_kW = Pshaft_W / 1000
omega_rad_s = n * 2*pi/60
torque_Nm = Pshaft_W / omega_rad_s
```

`n/120` is the four-stroke intake-event conversion from rev/min to cycles/s. The air-fuel ratio, gasoline-like lower heating value, displacement, volumetric efficiency, engine speed ranges, and thermal efficiency are generic assumptions, not a selected engine/fuel map. The latent `Pshaft = torque × angular_speed` identity is enforced by construction. No identity is promised for noisy observed measurements, or when a sensor fault targets RPM, power, or torque.

### Thermal and lubrication surrogate

The healthy temperature targets are:

```text
CHTtarget = Tambient_C + 75 + 0.72*throttle_pct
EGTtarget = Tambient_C + 170 + 3.4*throttle_pct
Tnext = Tcurrent + alpha*(Ttarget - Tcurrent)
alpha = dt/(tau + dt), dt = 1 s, tau = 25 s
```

The initial CHT/EGT/oil state is ambient temperature plus 25 °C. Oil temperature has a 60 s time constant and target:

```text
Toiltarget = Tambient_C + 45 + 0.22*throttle_pct + 0.10*thermal_fault_CHT_offset
```

Generic oil-pressure gauge value (reported in kPa):

```text
Poil_kPa = 180 + 90*(n/nrated) - 0.25*max(Toil_C - 90, 0)
```

The stated oil-pressure unit is kPa; the equation and coefficients are illustrative proxies. They are not sourced from an engine manual and are not limits.

Healthy vibration proxy is `0.25 + 0.004*throttle_pct` g RMS. There is no sensor mounting position, bandwidth, or spectral model.

### Physical-fault surrogates

For non-normal faults, `severity_level` is mild=1, moderate=2, severe=3 and `s = severity_level/3`. The fault is injected at `fault_onset_s` inclusive.

- **Combustion irregularity:** `q(t) = 0.65 + 0.35*sin(2*pi*t/13)`. During the active interval, thermal-efficiency factor decreases by `0.10*s*q`; speed factor decreases by `0.015*s*q`; vibration increases by `0.20*s` g RMS.
- **Efficiency degradation:** during the active interval, thermal-efficiency factor decreases by `0.15*s`, speed factor by `0.012*s`, and fuel-flow compensation increases by `0.04*s`.
- **Thermal abnormality:** during the active interval, the CHT target increases by `25*s` °C and EGT target by `75*s` °C. This thermal effect is coupled into the oil-temperature target as defined above.

These are designed, deterministic fault signatures, not diagnosed physical mechanisms.

### Synthetic sensor measurements and sensor faults

Each observed channel begins as its latent state plus independent zero-mean Gaussian noise with the per-channel standard deviation in the config. Sensor-integrity faults do **not** alter latent physical state:

- **Bias:** add `configured_channel_offset × severity_level` at and after onset.
- **Drift:** linearly ramp from zero at onset to the configured channel offset × severity level at the final sample.
- **Stuck:** repeat the previous noisy measurement from onset onward.
- **Dropout:** for the selected channel only, independently replace each active sample by NaN with probability 0.25. Every missing cell receives `measurement_missing_reason=injected_sensor_dropout`.

Sensor offsets and noise scales are arbitrary prototype settings, listed with units in config. Sensor faults are separate labels from the three physical-fault classes. For sensor-dropout scenarios, missing values are intentional; the processed features keep them missing, add channel-specific missingness flags, and leave imputation to a model pipeline fitted on training data only.

## Raw, labels, features, and lineage

- `data/raw/engine_twin_v0.2_raw.csv`: environmental inputs, latent state surrogates, matched healthy references, noisy/faulted measurements, and label metadata. Only measured channels represent simulated sensor readings.
- `data/processed/features.csv`: numeric predictors only. It contains operating conditions, phase one-hot columns, measured channels, residuals, and channel-specific missingness flags.
- `data/processed/labels.csv`: fault type, severity, active flag, onset/duration, sensor-fault target, and null RUL. Labels are never predictors.
- `data/processed/feature_lineage.csv`: feature row → raw row, scenario, engine, phase, split membership, and time. It is metadata, not a model feature table.

Every residual is computed as `measurement − matched healthy_ref` at the same operating point, using the same generic engine parameter set. No statistics or normalization are fitted across train/test. See `metadata/feature_pipeline.json`.

`metadata/data_dictionary.csv` lists raw columns, parsed type, unit, kind, and caveat. `metadata/parameter_register.csv` lists the assumptions and units. `reports/column_statistics.csv`, `reports/split_coverage.csv`, and `reports/validation_report.md` are regenerated by the validator.

## Baseline protocol and claims

`src/train_baselines.py` compares a majority-prior `DummyClassifier` and an imputation + Random Forest classifier. Model selection uses validation macro-F1; the selected model is refit on train+validation and evaluated once on the relevant test partition. Results include macro-F1, per-class precision/recall/F1, confusion matrices, binary fault-detection F1, sample-level metrics, and scenario-majority metrics.

- Scenario-held-out metrics measure new scenarios from the 18 training engines.
- Engine-held-out metrics measure scenarios from six different synthetic engine parameter sets.

These are evaluations against labels produced by the same simulator. They establish only the model's ability to reproduce this synthetic generator's labels; **they do not establish real-engine fault-detection accuracy**.
